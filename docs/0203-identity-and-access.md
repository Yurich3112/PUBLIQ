# Identity and access

## Responsibility and status

Keycloak owns credentials, MFA, identity profiles and realm roles. Better Auth
inside Next.js handles OIDC login and application sessions in `app_db` through
a custom Prisma/Keycloak identity adapter. Next.js must enforce business authorization. This is a design
contract with an implemented DEV baseline. Realm configuration and theme assets were adapted from the sibling;
the server-side login flow and live DEV integration are now implemented and
tested as described in the [login recipe](0304-keycloak-login.md). The Web client
is enabled with an exact v1 callback and S256 PKCE. The managed minimal client
definition contains Web and the read-only directory; no separate API-service
client is required for the combined Next.js backend.

The sibling repository's auth is partial and explicitly paused. Its custom
Valkey adapter and failed Web type check do not establish working auth here.
This PoC selects PostgreSQL sessions and does not resume or modify sibling work.

The [database package](0303-prisma-database.md) now implements the custom
application `User`, `Session`, `Account` and `Verification` schema and an initial
CLI-generated migration. Local keys are named `uuid` and generated by PostgreSQL
`uuidv7()`; user foreign keys are `userUuid`. `User` stores only a unique verified
`keycloakUuid` reference and timestamps, with no profile/password fields.
Keycloak remains the sole profile and credential source. The migration was tested on disposable databases and deployed to the DEV
application DB. Better Auth/Prisma bridging and server-side Keycloak login now
exist. Disposable-user OIDC/SSO logout and browser checks passed; acceptance of
every login-start path, production environment and business permission remains separate.

## Realm and clients

Use realm `modulon` with separate instances, clients and credentials in DEV, QA
and PROD. The managed hierarchy is `ROOT -> SADMIN -> ADMIN -> USER -> LOGED`,
plus independent `AUDITOR` (read-only audit/log review) and `VIEWER` (read-only
business access) roles. Neither independently grants admin entry or inherits USER.
`GUEST` is explicit limited access, not an anonymous fallback. A technical `SYSTEM` role
belongs to service accounts. Express inheritance through managed composites;
numeric level attributes alone do not grant application permissions. The server
maps verified role names through its own allowlisted levels. Application
`ROOT` is not a master-realm administrator.

| Client | Purpose | Allowed access |
| --- | --- | --- |
| `modulon-web` | Confidential OIDC client used by Better Auth in the Next.js backend | Authorization Code with PKCE, exact callback/logout URLs and selected profile/role scopes; no password grants |
| `modulon-directory` | Confidential service-account client for server-side Admin REST API reads | Minimum permissions for selected user/profile/role queries; no interactive login, `manage-users` or `realm-admin` |

No separate API client is needed for the combined Next.js backend. Keep client
secrets separate and server-only. Import/reconciliation are controlled setup
operations managing owned settings without replacing realms, deleting human
accounts or resetting existing secrets on startup.

## Custom themes

Version custom login/account themes under
`infra/local/keycloak/themes/modulon`, package them in the Keycloak image and
select them in the application realm. Use Modulon branding, PL/EN messages and
light/dark/system preferences. Review compatibility against the pinned Keycloak
version; a custom Admin Console theme is outside the baseline.

Preference cookies are UI state, never identity/authorization. Share Web/auth
preferences only with an explicit cookie domain and separate DEV/QA names.
Retain upstream/third-party notices for reused templates/assets. Copied theme
assets include their source LICENSE and NOTICE files. See the
[Keycloak theme guide](https://www.keycloak.org/docs/latest/server_development/index.html#_themes).

## Browser authentication and local identity

1. The browser starts sign-in through Better Auth in Next.js.
2. Keycloak authenticates the user. Next.js validates the response using state,
   PKCE, issuer, audience, expiry and nonce where applicable.
3. Link verified issuer/subject to a local user with a separate UUIDv7 ID. Do
   not substitute the Keycloak UUID or link solely by email.
4. Better Auth persists supported user/account/session/verification records in
   `app_db`. Keep required adapter fields even when values come from Keycloak;
   local profile copies do not become another credentials authority.
5. The browser receives an HttpOnly cookie, Secure on HTTPS, with deliberate
   SameSite/origin controls. Provider/directory tokens remain server-side and
   are excluded from public session responses.

Use the supported OIDC integration for the pinned Better Auth release; the
[Generic OAuth plugin](https://better-auth.com/docs/plugins/generic-oauth)
supports providers such as Keycloak. Validate adapter schema and UUID generation
before migrations. PostgreSQL sessions require no Valkey. This repo uses a custom
Prisma identity adapter to preserve UUID naming and Keycloak-owned profile data.

Application TTL/warning, bounded manual/navigation renewal and read-only 10-second
validity checks are implemented. Expiry automatically clears client state through
hard navigation. Local revocation and provider SSO logout are distinct; the manual
flow performs both and was tested with a disposable Keycloak account. Global
other-device/back-channel logout and a general expired-record cleanup job are not
implemented. See [session operation](0402-session-operations.md).

The local catalogue/UI allowlist is ROOT, SADMIN, ADMIN, SYSTEM, AUDITOR, VIEWER,
USER, GUEST and LOGED. Keycloak bootstrap renames legacy `ADMINISTRATOR` to `ADMIN`
in place, preserving its UUID and user/group/composite assignments. If both names
already exist, bootstrap stops rather than discard or silently merge assignments.
Managed composite links are reconciled exactly, including removal of obsolete
inheritance; independent roles have no composites. Numeric level attributes are
metadata only and are omitted for independent roles. Seeding the application
catalogue does not change Keycloak assignments. No audit-log endpoint is introduced
by declaring AUDITOR; each future read/write operation must enforce its permissions.
Role display reads effective Keycloak realm mappings on verification; no-role and
unavailable-directory states never assign a fallback realm role. A verified login
can meet a level-zero policy without assigning LOGED to the account. Business
authorization must still check the actual permitted server operation.

## Parameterized server access

`src/schemas/access.ts` is the application policy source. The managed realm
definition stores matching string-valued `level` attributes; regression tests
check agreement. Authorization uses the highest mapped level among verified
effective role names, not a number supplied by a browser or a raw token claim.

| Role | Application level |
| --- | --- |
| ROOT | 100 |
| SADMIN | 90 |
| ADMIN | 80 |
| USER | 50 |
| LOGED | 0 |

AUDITOR, VIEWER, SYSTEM and GUEST remain separate role names without an elevated
numeric mapping. Their names alone do not satisfy USER or administrative thresholds.
Anonymous/expired sessions have no authenticated level; they never satisfy zero.
LOGED is intentionally spelled as the configured role name.

`src/server/auth/access.ts` exposes `getAccess`, `requireAccess` and `withAccess`.
Policy accepts `requireLogin` (default true) and optional integer `minRoleLevel`
from 0 to 100. A supplied minimum also requires login. Public access requires
`requireLogin: false` with no minimum. With a valid session, a role-directory
failure can meet only level zero; positive thresholds fail closed.

The following fragment assumes a protected read returning an allowed DTO:

```tsx
import { ADMIN_ACCESS } from "@/schemas/access";
import { requireAccess, withAccess } from "@/server/auth/access";

// Layout/page boundary: ADMIN_ACCESS requires login and level >= 80.
await requireAccess(ADMIN_ACCESS);

// Repeat inside each Server Action; the layout is not inherited authorization.
return withAccess({ requireLogin: true, minRoleLevel: 80 }, async context => {
  if (!context.actorUuid) throw new Error("Verified actor required");
  return readAllowedData(context.actorUuid);
});
```

`requireAccess` uses the framework's unauthorized/forbidden boundaries.
`withAccess` returns `{ status: "denied" }` without invoking its callback when
access fails. Its server-only context contains the local actor UUID, role level
and verified roles. `withAdminSession` is a thin ADMIN_ACCESS mutation wrapper
that requires a non-null actor UUID. Clients never choose that actor.

The admin layout, pages, table reads, product creation and file mutations share
this policy. Request-local React memoization deduplicates session/role reads;
decisions are not cached across requests. Lowering ADMIN to USER in live Keycloak
was verified to deny the next table action while the session remained valid.
Thresholds simplify hierarchical entry checks; resource ownership and independent
business capabilities still need their own checks.

DEV reconciliation applied USER=50 and LOGED=0, including USER → LOGED, without
resetting volumes, accounts or assignments. Prisma migration
`20261112120000_logged_role` extends the local catalogue. The seed does not grant
roles to users. Use `pnpm stack:auth:sync` for owned realm changes and the separate
[Prisma workflow](0303-prisma-database.md) for the application catalogue.

## Identity data displayed in the application

Next.js routes/services expose permitted profile, directory and role data.
They authenticate callers, check permissions, validate filters/pagination, call
Keycloak Admin REST API server-side and return only allowlisted fields. Ordinary
users may see their own profile; listing others requires explicit permission.
Do not expose a generic Admin API proxy or browser-held service-account token.

Grant the directory client only permissions required by chosen endpoints.
Validate read/query permissions, such as `view-users` and `query-users`, against
the pinned Keycloak version; avoid unrelated event/admin permissions. Never
read Keycloak's database directly. See the
[Keycloak Admin REST API](https://www.keycloak.org/docs-api/latest/rest-api/index.html).

Return server-calculated capabilities for navigation, screens and actions.
Enforce the same rules in Route Handlers, Server Actions and business services,
including resource ownership. Plan role/capability refresh within 60 seconds;
protected operations refuse stale or unavailable authorization rather than
silently extending old grants. Verify role removal within that window.

## Evidence and remaining acceptance

The implementation checks cover signed OIDC/PKCE, disabled users, role display,
renewal caps/concurrency, expiry, CSRF and local-session replay rejection. A live
disposable-user check also verified Keycloak SSO logout and the next credentials
prompt. No existing user's password was requested or reset. See the
[recorded verification](0304-keycloak-login.md#recorded-verification).

The administration directory, file mutations and product list/create flow have
explicit level-80 server guards. Additional resource/cross-user business policies,
global/back-channel logout, QA/PROD and recovery remain separate scope.
Public session/status DTOs omit provider tokens; the standard RP-logout URL is a
separate, sensitive transport containing an ID-token hint. Never log its query.
