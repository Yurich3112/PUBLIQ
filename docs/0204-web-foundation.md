# Web foundation

## Implemented scope

`apps/web` uses Next.js 16.4.3, React 19.3.0, Tailwind CSS 4 and TypeScript.
It belongs to the root pnpm 12.15.0 workspace (`apps/*`, `packages/*`) with one
root lockfile and native-build policy. The empty package placeholders are not
workspace packages until they gain manifests. `packages/database` is now an
implemented Prisma workspace package; see the [database recipe](0303-prisma-database.md).

The sibling Web foundation was ported with these boundaries:

- `src/ui/basic`: native controls, buttons, typography, tables, dialogs, tooltips
  and shared Tailwind styles with per-instance overrides.
- `src/ui/components` and `src/ui/layout`: navbar/footer, language/theme/contrast
  selectors, providers, back-to-top, readiness indicator, Popup/Blur/CornerBadge,
  UserPanelV2 and shared session details/warnings.
- `src/config`, `src/schemas`, `src/cookies`: validated allowlisted public config,
  runtime config and safe UI preferences. The displayed version comes from this
  root package, which owns the system version.
- `src/i18n`, `messages/pl`, `messages/en`, `src/proxy.ts`: locale-prefixed routes,
  Polish default, matching translation keys and `next-intl` integration.
- `src/app/[locale]`: localized layout/homepage and `/pl/test`/`/en/test` component
  gallery. Authentication/session and private-avatar flows are implemented;
  admin user/file/product tables load data asynchronously. Product creation uses
  an optional image and a URL-controlled side panel. Broader business features
  remain separate work.
- `src/app/api`: public API discovery at `/api`, with `/api/v1/health/live` and
  `/api/v1/health/ready` as process/config checks only. They do not
  report PostgreSQL, Keycloak or S3 health.
- Branding assets, the favicon copied from Modulon at `src/app/favicon.ico`,
  and the repository's exact license text at `/LICENSE.md`.

The source `auth-button`, auth config, Valkey adapters, auth client and auth
routes were deliberately excluded. Better Auth now has a [server-side Keycloak flow](0304-keycloak-login.md)
with a custom Prisma adapter, bounded renewal, live role display and hard local/SSO
logout. Future integration must use the selected PostgreSQL/Prisma
storage and Keycloak contract, not the sibling's paused Valkey implementation.

The structure and API boundary review is recorded in
[Web structure](0206-web-structure.md). API routing stays outside the locale UI
layout; readiness logic lives in `src/server/health.ts`, with server-only HTTP
response policy in `src/server/http.ts`. Public/server config files are named
`public.ts` and `server.ts`; Web now explicitly declares ESM.

## Next.js feature configuration

`apps/web/next.config.ts` enables stable `reactCompiler: true` and
`typedRoutes: true`, alongside the existing `cacheComponents: true` and
`partialPrefetching: true`. The compiler uses the pinned Babel plugin; the
experimental Rust compiler is not enabled. Typed routes are generated by
`next typegen` and checked by TypeScript, including navigation consumers.

View Transitions are available in this React 19.3 stack without an experimental
flag; no transition components or animations were added by the configuration
change. Auth interrupts and the other TrueGuard-specific experimental settings
remain outside this configuration until a concrete integration needs them.

Native install scripts are explicitly allowed only for `@parcel/watcher` and
`@swc/core` in the root pnpm build policy; existing disabled entries were
preserved. Package versions match the source foundation while Next.js/React
retain the versions generated in this repository.

## Local commands

Run from the repository root:

```powershell
pnpm install --frozen-lockfile
pnpm dev
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

Open `http://localhost:3000/pl` or `/en`; `/` redirects to `/pl`. Configuration
uses safe defaults; `apps/web/.env.example` documents the public preference names,
port and timezone. The ignored `.env` was initialized from that safe example
without replacing an existing file.
Default `modulon_poc_*` preference cookies are separate from the sibling's names.
No source application env file or authentication secret was copied. `pnpm dev`
now runs the [shared DEV startup](0315-dev-startup.md), including Docker readiness,
builds, guarded migrations and all host services. `pnpm dev:web` starts only
Next.js from a prepared checkout. DEV shares only UI preference cookies across
`modulon.local` subdomains so Web and Keycloak use the same theme. Authentication
cookies remain host-only. Leave the preference domain empty for localhost-only UI work.

## Verification and remaining work

Passed after the API/structure changes: root `pnpm check` (types, lint and 35
tests), release build and QA Compose configuration validation. Tests include
13 script tests, 12 preference/config/catalog tests, 3 API health/response tests
and 7 basic-component tests. HTTP checks against temporary production servers
verified API discovery, nonlocalized health, no-store headers, rejected POST,
API 404, PL/EN pages, exact API-prefix matching and the retired old health URL.
Invalid runtime configuration returned redacted readiness 503 while liveness
remained 200. Both temporary servers were stopped.

That paragraph records the earlier structural slice. The latest implementation
slice passed 107 Web tests and 18 script tests plus types/lint, OIDC/DB integration
and isolated product/table/role browser checks. Earlier PL/EN session checks and
disposable-user live Keycloak SSO logout also passed. It did not repeat the release
build over the running dev output. The [UI recipe](0306-ui-components.md) and
[session runbook](0402-session-operations.md) describe current behavior and limits.

Prisma schema/client and DEV migrations are applied. The five-service DEV infrastructure
is adapted, and private avatar storage is implemented. Admin server access policies,
file permanent deletion and product creation are implemented; broader resource
policies, stored product-image delivery and PROD recovery remain separate work.
Durable queue execution and local QA build/migrate/start workflows are described
in their owning recipes; these earlier Web checks do not establish their full
acceptance. No cloud deployment is implied by these local checks.
