# Server-side Keycloak login

## Implemented flow

1. The navbar resolves the session on the server in a request-time Suspense boundary.
   A small client form manages pending state and the unavailable dialog. Anonymous
   visitors see **Sign in**; authenticated users get a 150px user dropdown with
   their first name (email fallback), profile details, roles, countdown, Keycloak account
   link and confirmed sign-out. UserPanelV2 first expands its identity row by 200px
   to the left, then unfolds details downward; both stages reverse when minimized.
   Its blurred backdrop, header and Escape support dismissal, with viewport clamping
   and reduced-motion support. Labels and dialogs support PL/EN. See
   [Account profile and avatars](0305-account-profile-and-avatars.md).
2. The sign-in Server Action validates the locale, invokes Better Auth's server
   API for provider `keycloak`, propagates state cookies through `nextCookies()`
   and redirects to Keycloak. Callback/error URLs are constructed server-side.
   A failed start returns action state and opens **Sign-in is unavailable** on the
   current page. A provider callback failure returns to the localized home page
   with `?auth=unavailable`, opens the same dialog and removes the error parameters
   from browser history. There is no separate login-error page.
3. Keycloak performs authentication. Better Auth handles the callback under
   `/api/v1/auth/callback/keycloak`, checks OAuth state, PKCE and the OIDC ID token
   using discovery/JWKS, including issuer, audience and nonce.
4. Only verified Keycloak identities may provision/sign in. Account linking,
   password login and local profile mutation endpoints are disabled. The local
   user stores `uuid`, verified `keycloakUuid` and timestamps. New local primary
   keys are generated by PostgreSQL `uuidv7()`; foreign keys remain `userUuid`.
5. An HttpOnly, SameSite=Lax, host-only cookie identifies the PostgreSQL session.
   HTTPS uses Secure cookies. Profile fields are hydrated from the read-only
   Keycloak directory on demand; they are not copied into database columns or a
   Better Auth cookie cache. Access/refresh tokens are encrypted before database
   storage. The pinned library stores the ID token as issued; treat technical
   account records and exports as sensitive. The logout token helper accepts
   either plain or encrypted stored ID-token values.

The custom adapter in `src/server/auth/adapter.ts` bridges Better Auth's logical
`id`/`userId` and provider fields to the existing Prisma schema. The public
session DTO uses `uuid` naming and omits session/provider tokens, email and
internal account records. Session data is never stored in a shared Next.js cache.
React `cache()` is used only for deduplication inside one server request.
The navbar button uses the shared green `success-outline` style: transparent
background with a green border/text, filled green on hover. The native modal
provides focus trapping, Escape and a translated Close action.
Next.js sign-in/sign-out pending states use the basic `Throbber`. The native
Keycloak submit control displays the matching 14px/one-second ring and localized
status, sets busy state synchronously before navigation and blocks repeat submits.
The original submitter name/value stays intact. Cancelled submissions and BFCache
restoration clear pending state; reduced-motion preferences disable rotation.

OIDC tokens may themselves carry profile claims; technical token storage is
not a second editable profile. No independent local profile/password record is
introduced. Keycloak profile or enabled-state changes affect subsequent directory
reads. A missing/disabled directory user fails closed.

## Registration, language and theme

The managed realm enables self-registration. **Register** / **Zarejestruj się**
on the Keycloak login screen opens its native registration form. Required
Keycloak profile fields remain visible; profile and password data stay in Keycloak.
This does not enable Better Auth's local registration or password endpoints.

The sign-in Server Action passes the validated application locale as `ui_locales`
and the selected `light`, `dark` or `system` preference as `modulon_theme`.
Keycloak consumes the theme hint, removes it from browser history, and preserves
the preference through registration, language changes and return to Web.
The system preference follows the browser's color scheme.

Web and Keycloak use the same preference-cookie name (`modulon_poc_theme` in DEV)
and `UI_PREFERENCE_COOKIE_DOMAIN=modulon.local`. QA uses its separate
`modulon_qa_theme` name. Old host-only theme cookies are removed during migration
to prevent duplicate preferences. Only UI preferences use the parent domain;
authentication/state/session cookies keep their existing scope.

Sign-in, registration and form submit actions have green outlines and fill green
on hover. Theme, language and navigation controls use neutral outlines and fill
with their text color on hover. Translations are provided by Keycloak's PL/EN
catalogues and the custom theme messages.

Apply realm/theme changes with `pnpm stack:up`; bootstrap runs in the existing
Keycloak container. Automatic DEV starts the four core infrastructure services
plus S3 console; the latter uses its own operator login.

Verification after this change: Web types/lint, 26 Web tests and the disposable
OIDC integration test passed, including forwarding of locale/theme parameters.
An isolated Edge profile verified the live DEV login and registration screens
for PL/dark, EN/light, PL/light, EN/dark and PL/system: registration link and
required fields, outline/hover colors, locale/theme controls, shared preference
on return to Web, and no horizontal overflow at 390px. No registration was
submitted and no human account was created or changed. The temporary profile
was removed; Keycloak was rebuilt and all four DEV containers are healthy.

## HTTP boundary

| Endpoint | Access |
| --- | --- |
| `GET /api/v1/auth/callback/keycloak` | Provider callback protected by OAuth state/PKCE/OIDC checks |
| `GET /api/v1/auth/get-session` | Own session DTO or `null`; no-store, no tokens |
| `GET /api/v1/auth/session-status` | Verified expiry, server time, public UUIDs, renewal policy/count and own role labels; read-only |
| `POST /api/v1/auth/sign-in/social` | Exact configured Origin required; only configured provider is available |
| `POST /api/v1/auth/renew-session` | Authenticated, exact-Origin renewal with warning/navigation and atomic-cap checks |
| `POST /api/v1/auth/hard-sign-out` | Signed-cookie logout, expected-session/lease protection and fixed provider/home destination |
| `POST /api/v1/auth/sign-out` | Delegates to hard logout at the HTTP boundary |

Other auth paths return 404; GET does not perform sign-out. Server Actions also
retain Next.js Origin/Host protection. Locale values are validated, and client
supplied redirect destinations are not accepted by the navbar actions.
The HTTP auth handler returns generic failures without provider response bodies.
Better Auth logging/telemetry are disabled; DEV Next.js incoming auth request and
Server Function argument logs are suppressed to avoid logging OAuth parameters.

The in-memory limiter allows ten sign-in attempts per minute and a global auth
limit of sixty requests per minute per library request key. This is per process,
not a shared limit across replicas. Existing Nginx application/API routing limits
are separate; this change does not claim a distributed auth limiter.

## Local operation

Use `apps/web/.env.example` for the full `AUTH_*` and `SESSION_*` contract. Web receives only its
client secret, read-only directory client secret, application DB URL and its own
Better Auth secret. It never receives Keycloak administrator or PostgreSQL
superuser credentials. Real values remain in ignored env files.

| Variable | DEV value/purpose |
| --- | --- |
| `AUTH_BASE_URL` | `https://modulon.local`, the canonical application origin |
| `AUTH_SECRET` | Independent random secret of at least 32 characters |
| `AUTH_ISSUER` | `https://auth.modulon.local/realms/modulon` |
| `AUTH_CLIENT_ID` / `AUTH_CLIENT_SECRET` | Confidential `modulon-web` client |
| `AUTH_DIRECTORY_URL` | `https://authconsole.modulon.local/admin/realms/modulon` |
| `AUTH_DIRECTORY_CLIENT_ID` / secret | Read-only `modulon-directory` service account |
| `AUTH_COOKIE_PREFIX` | `modulon_poc_auth`; isolate QA/PROD prefixes |
| `SESSION_TTL` | Seconds per application session/extension; default 900, bounded to 300–28800 |
| `SESSION_WARNING` | Warning threshold in seconds; default 120, strictly below TTL |
| `SESSION_AUTO_REFRESH` | Literal `true`/`false`; default false; non-home navigation renewal |
| `SESSION_MAX_REFRESHES` | Total successful manual/navigation extensions per session; default 3; 0 disables renewal |

### Session lifecycle and role display

The Web client verifies its session immediately after mounting through Better Auth's
`GET /api/v1/auth/session-status`, then every 10 seconds while visible and on focus or
returning to the tab. The UI counts down every second using server time to correct
client clock differences. Reads do not extend expiry: Better Auth's
[`disableSessionRefresh`](https://better-auth.com/docs/concepts/session-management)
is enabled and cookie caching is disabled. Network failure shows verification as
unavailable; an authoritative 401 marks the session inactive. A local countdown
is presentation only; the server validates every session and renewal.
Effect cleanup cancels its request without showing a verification error. A new
effect starts a fresh immediate check; late results from older requests are ignored.
Actual timeouts, network failures and service errors still show unavailable status.
Here read-only means non-renewing verification of an active session; Better Auth
may clear cookies or remove an expired record as part of rejecting an invalid session.
The status DTO includes only public UUIDs and lifecycle/role values, never tokens.
A different session/user UUID (for example after another tab switches accounts)
refreshes the server-rendered identity instead of mixing profiles and role labels.

`POST /api/v1/auth/renew-session` is a Better Auth plugin endpoint with authenticated
session middleware, exact-origin checks and signed cookie updates. Manual renewal
is accepted only during the warning window. With `SESSION_AUTO_REFRESH=true`,
navigation between localized non-home pages may renew; `/`, `/pl`, `/en` and their
trailing-slash home variants never renew. Initial render, reload and polling are
not navigation renewals. Keep TTL short in navigation mode, for example 900 seconds
(15 minutes). With false, navigation has no renewal side effect.

The database counter covers both renewal modes across all tabs. A conditional,
atomic update checks the current expiry and count, so concurrent requests cannot
exceed the limit. Navigation requests within 10 seconds of a full TTL are coalesced
without using another renewal. Expired/revoked sessions cannot be revived.
The additive `session_renewal_counter` migration was generated and applied using
Prisma CLI; existing sessions start with zero renewals. Restart Web after changing
policy values. TTL applies to newly issued sessions and successful extensions;
changing it does not retroactively rewrite existing session expiry dates.

Below the warning threshold, the collapsed dropdown shows a top-right countdown
badge and an expiry-warning Popup opens once per expiry. Its actions are Sign out
now, Understood and Extend session, in that desktop order with red, standard and
yellow outline tones, with semantic fill and contrasting icons on hover. Shared
`buttonMotion` applies a 200 ms transition and respects reduced motion.
On narrow screens they stack in the same order. Acknowledgement
dismisses the current warning. The renewal action stays visible and disabled
after the shared limit is reached. Renewal/logout disable all actions and closing
until the operation settles. See the [UI contract](0306-ui-components.md#session-warning-actions).
Expiry or an authoritative 401 automatically signs out and performs a full-document
navigation; no confirmation click is required. UserPanel's `SessionDetails`, `SessionWarning` and lifecycle
hook share one status source. Preview mode on `/pl/test` and `/en/test` never calls
session endpoints or performs account/logout mutations.

Role labels come from Keycloak's effective
[realm role mappings](https://www.keycloak.org/docs-api/latest/rest-api/index.html),
filtered to the application's nine role codes. No assignment displays **No role
assigned**; directory failure displays **Roles are currently unavailable**. Neither
case grants a fallback USER/GUEST role. This is role display, not a replacement for
server authorization. Application renewal does not extend Keycloak's separate SSO
session. Manual provider logout is implemented as described below; global logout
of other devices and back-channel logout remain separate work.

The checkout's missing auth env values were initialized using its local client
secrets plus a newly generated application secret; existing values were preserved.
The Web client is now enabled in the managed realm, with Authorization Code only,
PKCE S256 and the exact versioned callback. Directory access was verified live.
Existing human accounts/passwords and existing client secrets were not replaced.

The initial Prisma migration was applied through `pnpm db:deploy` to the confirmed
DEV application DB `modulon` in stack `modulonpocdev`; `pnpm db:status` passed.
The Keycloak database was not migrated by application Prisma.

```powershell
pnpm dev
```

Open **https://modulon.local/pl** or **https://modulon.local/en**, then click
**Sign in**. Use an existing Keycloak account with an email address. Better Auth
requires an email for the OIDC flow; the email remains sourced from Keycloak.
Use the canonical HTTPS origin rather than the host listener's localhost URL.

Both root and `apps/web` dev/start commands use `scripts/web.mjs`. For configured Modulon local
domains it supplies the absolute local CA path via `NODE_EXTRA_CA_CERTS` before
starting Node/Next.js. There is no TLS-verification bypass. Browser trust and hosts
entries remain workstation prerequisites. Restart Web through the root command
after introducing this configuration; a running process cannot acquire this
startup trust setting through `.env` hot reload. Direct package commands such as
`pnpm --filter web dev` therefore also use the shared launcher. The login button
always retries the current Server Action; a previous session-read failure does
not lock the UI into an unavailable state.

QA/PROD must explicitly supply the same server-only settings with their own
origins, secrets/cookie prefixes and private PostgreSQL connection URL. The
QA Compose Web service has its Dockerfile and explicit auth/DB runtime wiring;
see [QA containers](0316-qa-containers.md) for startup and recorded verification.
That local implementation is not full environment acceptance. PROD deployment
remains a separate task.
Public discovery/issuer/callback URLs must remain browser-reachable and trusted
from the Web container as well.

## Admin route authorization

`/pl/admin` and `/en/admin` use a server-side admin layout. The shared
`requireAdminAccess()` guard first resolves the current Better Auth session,
checks expiry and only then reads effective Keycloak realm roles for that verified
identity. Only `ROOT`, `SADMIN` or `ADMIN` permits access. Empty roles, failed
verification or unavailable directory access grant nothing. Keycloak now manages
`ROOT -> SADMIN -> ADMIN -> USER -> LOGED` through recursive composites; effective-role
queries include inherited roles. Bootstrap renames legacy `ADMINISTRATOR` to
`ADMIN` in place, retaining role UUID and existing assignments. No new human role
assignments are seeded. VIEWER and AUDITOR remain independent of this hierarchy.

The shared [parameterized access policy](0203-identity-and-access.md#parameterized-server-access)
maps ROOT=100, SADMIN=90, ADMIN=80, USER=50 and LOGED=0. Admin entry uses
`requireAccess(ADMIN_ACCESS)` with a minimum of 80; `requireAdminAccess()` delegates
to that policy. `withAccess(policy, callback)` protects Server Actions, and
`withAdminSession` supplies the same admin threshold and verified actor. Unknown
roles do not gain an elevated level. A missing/expired session never becomes level 0.

The guard invokes Next.js `unauthorized()` for missing/expired sessions and
`forbidden()` for insufficient/unavailable authorization, using the matching
localized access UI. The administration area includes a Keycloak user directory
and the [file catalog](0307-admin-files.md) and [products](0309-admin-products.md). UserPanel V1/V2
shows a localized administration link only while its verified session is active
and its current role list includes ROOT, SADMIN or ADMIN. Missing/unavailable roles
hide the link. This presentation uses the same role allowlist as the server guard;
the server still authorizes direct URLs independently. Gallery previews disable
navigation through the link.

The existing lifecycle verification also reacts to role changes during an open
session. At the next visible 10-second check, focus/visibility check or route
change, loss of all admin roles on `/admin` or its descendants performs a full
replacement navigation to localized `/access-denied`. A failed verification also
leaves the protected document; it does not revoke an otherwise valid session.
Role changes on other pages refresh server-rendered navigation so grants and
revocations update the navbar without another login. This is polling, not server
push; server guards still enforce every protected operation independently.

The layout wraps request-time verification in Suspense and reveals its children
only after access is granted. The page also invokes the same guard before its
content. Next.js layouts may persist between navigations and do not prevent
parallel child execution: every protected data read, Server Action or API
handler must enforce authorization independently. Existing user/file/product
reads and mutations do so. React request-local memoization
deduplicates the current render; decisions are not stored in a shared cache.

Focused checks cover session-before-role ordering, expired/missing sessions,
all nine application role codes, missing/unavailable roles and explicit rejection
of the obsolete `ADMINISTRATOR` string outside the managed migration. Earlier
browser checks exercised anonymous redirects and PL/EN denial pages before
the request-time guards adopted the current unauthorized/forbidden boundaries.
A live disposable-account browser check additionally verified ADMIN
entry, changing ADMIN to USER in Keycloak while the panel remained open, automatic
exit/removal of the navbar link with the session preserved, and restoration after
regranting ADMIN without another login. Its account/local rows/browser were removed.

## Logout and acceptance limits

**Sign out revokes the current application session/cookies and starts Keycloak
RP-initiated logout.** UserPanel calls the Better Auth `POST /api/v1/auth/hard-sign-out`
endpoint, then uses `window.location.assign()` instead of a client-router redirect.
The server loads the stored ID-token hint through Better Auth's token helper and constructs the configured issuer's
logout URL with an exact localized return (`/pl` or `/en`). Those two URLs are
allowlisted in the managed Keycloak client. Public `/sign-out` requests delegate to
the same endpoint; the Server Action fallback also uses it.

The endpoint requires exact Origin and a signed session cookie or a signed,
opaque logout-only cookie before resolving provider context. A supplied session
UUID is compared with that verified context:
an older tab cannot revoke a different/newer identity. An expiry request also checks
the database expiry before deleting; if another tab renewed the lease, the client
rechecks instead of logging out. Session deletion and cookie expiry precede provider
navigation. The logout URL contains the standard ID-token hint; never log its full
query string. Nginx uses its existing query-free safe access-log format.

The callback captures the original ID-token hint in an encrypted `Verification`
record, addressed by the hash of a random handle. Only the signed opaque handle
is stored in the HttpOnly logout cookie. This context survives application-session
expiry by 300 seconds and is consumed on logout. Active session checks backfill
older sessions; renewal updates its expiry. It cannot authenticate or renew a
session. No schema migration is required. A server-only status helper allows a
reload after session-cookie expiry to render the blocking logout progress and
finish provider logout; the helper is not publicly routed.

Local cleanup expires this application's auth namespace, including chunked names,
host/domain variants and `/`, `/api/v1/auth`, `/api/auth` paths. UI theme, locale
and contrast preferences remain. Keycloak clears its own cookies through the
provider redirect; the application cannot delete another host's cookies directly.

At zero remaining time or an authoritative 401, the client invokes this endpoint
once and uses `window.location.replace()` to clear protected client state without
requiring a Popup dismissal. Before sending the request, it paints a blocking
SessionLogoutProgress Popup with localized signing-out text, Throbber and blurred
backdrop. It has no header, X, footer or buttons; Escape/backdrop cannot dismiss it.
The returned logout URL is executed while this progress state remains visible.
Background tabs have a bounded paint-readiness fallback so logout cannot stall.
Transient polling failures alone never trigger logout.
If both the session cookie and valid logout-only context have disappeared, the endpoint clears
remaining local cookies and returns home without guessing a provider identity.
An automatic logout request failure still returns home; a manual failure keeps the
confirmation open with a retryable error. During manual sign-out, the confirmation
shows localized signing-out text and a throbber, disables both action buttons
and blocks Escape/backdrop dismissal through `disableClose`. X is hidden while
pending. Reopening after a failure clears its old message. Preview mode never
signs out. Isolated browser checks verified these interaction states using a
simulated logout response, separately from live provider logout acceptance.

Sign out now in the warning uses the same manual hard-logout path. If expiry
occurs during that request, the warning stays blocked while `logoutPending` is
true. Automatic expiry logout waits for the current request. When a manual
request fails after expiry, the lifecycle effect resumes automatic logout and
shows its blocking progress Popup. The redirect guard keeps those requests
sequential. A focused browser fixture verified this handoff using the real hook
and simulated API responses.

Other application sessions/devices remain independent. Realm-wide/global and
back-channel logout and resource-level policies beyond the implemented admin
threshold and file/product reference checks remain separate work.

and 51 tests (14 tooling, 3 database, 34 Web). The focused integration command also
passed. The subsequent products/access/table slice passed 107 Web tests, 18 script


then removes both. It covers PKCE/verified callback, rejection of an incorrect

immediate replacement requests, genuine 503/recovery and absent/broken avatar

repeated over the active dev `.next` after the latest auth changes. These results
do not establish every login-start path, QA/PROD or recovery acceptance. Use the
